CLI-first · Local-first · Agent-native

Fast, local project management — without the ceremony.

Vektor is for individuals and small teams who want to go fast. Projects, issues, and comments in a desktop app with a killer command line, first-class local support. No server or account required, no setup, and no sprint planning. When you want to share it, the same binary hosts a server and the same app points at it.

What it looks like

# the window, over ~/.local/share/vektor — nothing to configure
$ vek app

$ vek issue create --project VEK --title "Wire up the board view"
VEK-54  Wire up the board view  ·  backlog  ·  none
$ vek issue move VEK-54 in_progress

# a bare number works when a default project is set
$ vek issue view 54

# --json on every command, mutations included
$ vek issue list --json | jq -r '.[] | select(.priority == "urgent") | .ref'

# from a Forgejo or GitHub export; issue numbers are preserved
$ vek import --file backlog.json

Every command runs against the local file with nothing else running, in about 20 ms.

How it works

Local mode

The default. Data is a SQLite file under ~/.local/share/vektor; whoever can read the file is the user, just like a git repository. Identity comes from git config user.email.

Server mode

The exact same app pointed at a hosted instance and authenticated by an API token the machine holds. You can toggle it in Settings or with vek config set-server. Switching never moves data.

One UI, two hosts

The web UI is embedded in the binary. vek app shows it in a native window and vek serve serves it to a team. It's the same code, same behaviour, no feature the browser cannot do.

Two builds, one module

vek desktop links the OS webview for the window. vek headless is pure Go and static built for servers and CI with every command except vek app. Copy it to a machine and it is just vek.

Small on purpose

It has projects, issues, labels, comments, status, priority, and assignee with references like VEK-53. Import from a forge export. Backups are sqlite3 .backup. That is the whole data model.

Not a forge

Code, pull requests, review, and CI stay on Forgejo, GitHub, or wherever they are. Vektor links out and never mirrors.

The desktop app

vek app is the web UI in a native window over your local data. It is the whole product on one machine. Deliberately, it is nothing more than what the browser gets: no native-only features beyond the window itself, so there is only one UI to keep honest.

  1. Launch

    Run vek app, or click the icon. The window opens on your issues in well under a second; a 25 MB binary linking the webview your OS already has, not a bundled browser. No login, no account, and no first-run wizard.

  2. Look around

    A sidebar of projects; a list grouped by status; a board of status columns over the same filters; an issue view with the description, comments, and the branch chip that links out to your forge. Filters live in the URL, so a view is a link you can paste. Bodies and comments render as beautiful markdown, and VEK-53 or #53 in text is a link inside the app.

  3. Work without leaving the keyboard

    j/k to the issue, s to change status, p priority, a assignee, x to finish it, u if you didn't mean to. i edits the title in place, e the description, r replies. ⌘K finds anything across projects. Every change applies instantly and reverts if the write fails.

  4. Use the terminal alongside it

    With the window open, vek issue move VEK-53 done in a shell shows up in the window at once. The CLI finds the running app and routes through it rather than going around it. Terminal and window are two views of one thing.

  5. Make it yours

    Settings → Appearance: a preset (Ember, Rose, Gold, Moss, Sky, Indigo, Slate) or your own three sliders; light, dark, or follow the system; a density control that scales the whole interface.

  6. Point it at a server, later

    Settings → Desktop: switch from Local to Server, paste the URL and a token, and the same window is now looking at a hosted instance while it stays open. Switching doesn't move data; when you want your local issues on the server, vek import carries them over with their numbers. If you switch back, the server URL is remembered.

One runtime dependency on Linux — WebKitGTK 4.1, which most desktops already have; macOS uses WKWebView and Windows WebView2, both built in. A headless build of the same binary, without the window, has no dependencies at all and is what runs on servers and in CI.

Deploys in seconds

When one machine stops being enough, the same binary is the server. One container, one SQLite file, no database service, no queue, no object store — the whole thing fits on the smallest box in the homelab. 

# docker-compose.yml
services:
  vektor:
    image: forge.coltco.net/austin/vektor:latest
    ports: ["8659:8659"]
    volumes: ["vektor-data:/data"]
    environment:
      VEKTOR_LOCAL_AUTH: "true"
      VEKTOR_SESSION_SECRET: "change-me"
    restart: unless-stopped
volumes:
  vektor-data:

$ docker compose up -d
$ vek config set-server https://vektor.example.com
  • One image, one process. A static Go binary on Alpine, running as a non-root user, with a healthcheck.
  • Your data is only yours. Everything lives in the /data volume. Back it up with sqlite3 .backup and restore it by copying it back.
  • Local accounts or OIDC. Start with local auth and nothing else. Point it at Authentik, Authelia, or any OIDC provider when you want SSO.
  • Devices, not sessions. The desktop app and the CLI authenticate with an API token you mint once.
  • Behind your proxy. Plain HTTP on one port; TLS, hostnames, and access rules stay with Caddy, Traefik, or nginx where they already are.
  • Or no Docker at all. Copy the headless binary to the machine and run vek serve. It is the same vek.

The CLI is the agent interface

There is no MCP server. The command line was built so that a person, a script, or an agent can drive it from --help and a SKILL.md alone.

  • --json on every command, mutations included. Create an issue, get the ref back as data.
  • One structured error shape, shared with the HTTP API: {"error", "message", "details": [{"field", "message"}]}.
  • Human refs everywhere. The CLI never handles a UUID.
  • No prompt traps. --password-stdin, --body; nothing opens $EDITOR or waits on a TTY unless there is one.
  • Zero setup. Local mode has nothing to log in to and nothing to configure.

Themes are hue, chroma, and tint. Ember by default; Rose, Gold, Moss, Sky, Indigo, Slate; or your own on a slider.

What Vektor won't make you do

Vektor wants to capture the data, not build the ceremony. Dates, history, and metrics are welcome, but rituals are not.

  • Plan sprints. No cycles or velocity to bother you. Work is a list with a status.
  • Maintain a roadmap. There is no timeline view to maintain, and no initiative hierarchy. Bring your own plan; the issues are just the record.
  • Triage notifications. Nothing harasses your attention. Ask vek issue list or open the window.
  • Administer permissions. No roles or per-project access matrix. On a hosted instance, an account is just an account.
  • Move your code. Vektor is not a forge. Code, PRs, review, and CI stay where they are.

Where it stands

Under active development and not yet released. Direction has been settled with desktop and local support first, then server afterwards. Phase one, the local CLI and the desktop app, is being built now. The issues on Forgejo are the live backlog, and the README in the repository is the technical documentation.
